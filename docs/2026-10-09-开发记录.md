## 三、未跑通的 4 个用例及原因

以下 4 个用例（2 题 × C / C++ 各一次）未通过，均为题库测试数据本身的问题，判题引擎与参考解均正确，数据未改动。

### 旋转链表（第 32 题，`questions[31]`）—— C / C++ 各 3 个「500节点」用例，score=85

用例「500节点k=499 / k=500 / k=1000」的输入写成 `[1,2,3,...,500]`，期望输出写成 `[2,3,4,...,500,1]`。其中 `...` 不是 LeetCode 合法输入格式：判题侧所有语言的解析器都把 `...` 当占位符跳过（Java `CodeRunner` 与 C/C++ 解析器行为一致），因此输入只解析出 4 个节点 `[1,2,3,500]`，旋转后输出 `[2,3,500,1]`；而期望输出里同样含 `...` 字面量，无法与真实数字匹配。属于用例数据用了 `...` 简写、解析器不支持展开导致的格式问题。

### 最大子数组和（第 36 题，`questions[35]`）—— C / C++ 各 1 个「大正小负」用例，score=95

用例「大正小负」输入 `nums = [10,-1,10,-1,10]`，期望值为 29。该输入所有连续子数组和的最大值为 10−1+10−1+10 = 28，期望值 29 与输入不符，是期望值本身写错。

## 四、技术要点

1. **统一 LanguageHandler 分发**：`DockerJudgeEngine` 不再关心具体语言，全部交给 `LanguageHandlerRegistry.get(question.language)`，Java / C / C++ 共用一条判题链路。
2. **编译产物可执行位**：容器内运行 `./main` 需要二进制可执行，打包时对编译产物设 0755、其余文件 0644，否则 `Permission denied`。
3. **单翻译单元编译**：C/C++ 用 `main.c/.cpp` 直接 `#include "solution.c/.cpp"`，辅助头文件按签名词边界匹配引入。
4. **冒烟测试走真实链路**：`MultilangTestRunner` 复用 `JudgeService.trigger` 异步判题 + 轮询，不 mock Docker / 数据库，保证与线上判题一致。
