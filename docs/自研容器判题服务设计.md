## 四、核心流程（DockerJudgeEngine.judge）

1. 按 `submissionId` 取 `submissions` + `submission_details` + `question`
2. 生成 `Main` 包装类：读 stdin → 调 `Solution.methodName(...)` → 打印结果
3. 写临时工作目录，挂载进容器执行 `javac` 编译
   - 编译失败 → 状态 `COMPILE_ERROR`，回写 stderr
4. 编译成功 → 逐用例 `java` 运行，stdin 喂 `input`，比对 stdout vs `expected`（trim）
   - 超时 → `TIMEOUT`；非零退出 / 运行时异常 → `RUNTIME_ERROR`；内存超限 → 对应状态
5. 按通过率算 `score`，组装 `List<TestCaseResult>` 回写 MongoDB
6. 触发 AI 白盒评审，回写 `aiReview`（复用 [AiReview](file:///home/xyx/桌面/大创/1/codejudge-platform/backend/src/main/java/com/codejudge/platform/entity/AiReview.java) 结构）
7. 同步更新两库状态

## 五、Docker 隔离参数（安全关键）

```
--network none      # 禁网
--memory {memoryMb}m --cpus 1
--pids-limit 64     # 防 fork bomb
--read-only --tmpfs /tmp
--cap-drop ALL --user nobody
--rm                # 用后即焚
```

镜像：`openjdk:17`。工作目录通过 `docker run -v` 挂载宿主临时目录或 `docker cp` 写入。

## 六、风险点与待决问题

1. **方法签名缺口（最关键）**：题目只存 `methodName="sum"`，未记录参数个数/类型，`Main` 包装需要知道 `sum` 是否为 `int sum(int, int)`。→ 需扩充 Question 模型加 `methodSignature`（或 `paramTypes`）字段；老题是否兼容需定。
2. **容器冷启动慢**：每次 `javac` + `java` 都要启容器/JVM，单用例可能几百 ms～秒级。第一版建议「一题一次编译 + 多用例在同一容器顺序跑」，非每用例重启容器。
3. **输入解析约定**：`input="1 2"` 需按签名拆参。第一版按「空格分隔 + 全 int」约定，覆盖现有题目。
