## 一、今天已完成

### 1. 容器判题支持全部 Node 四种形态

**问题**：之前容器只能判普通类型（int/String/数组/ListNode/TreeNode），图（Node with neighbors）、N 叉树（Node with children）、随机指针链表（Node with random）、带 next 的二叉树（Node with left/right/next）四种 Node 形态全部报错「暂不支持的 Node 形态」。

**根因**：Node.java 包含所有字段（val/next/random/children/left/right/neighbors），`nodeKind()` 检测时 `random` 排第一，永远返回 `RANDOM_LIST` 而非正确形态。且 `DockerJudgeEngine` 没把辅助类传给 `generateMain`。

**修复**（`CodeRunner.java` + `DockerJudgeEngine.java`）：

- `DockerJudgeEngine`：先获取辅助类源码再传给 `generateMain`，使 Node 形态检测生效
- `hasAllNodeFields()`：判断 Node 类是否包含所有字段（无法区分形态时触发推断）
- `detectNodeKindFromSignature()`：从方法名/返回类型推断 Node 形态
  - `random`/`copyrandom` → RANDOM_LIST
  - `next`/`connect` → NEXT_TREE
  - `graph`/`clone` → GRAPH
  - 返回类型是 List（非 Node）→ NARY_TREE
  - 默认 → GRAPH
- Node 类 `children`/`neighbors` 默认初始化为 `new ArrayList<>()`，防止 NPE
- `parseClassFields` 正则支持 `= ...` 初始化语法

### 2. N 叉树解析/序列化重写

**问题**：`parseNaryTree` 按「每个节点后紧跟其子节点」格式解析，但 LeetCode 的 N 叉树序列化是「层序遍历，null 分隔每层」。

**修复**：
- `parseNaryTree`：改为层序解析，null 分隔每层，子节点按顺序分配给当前层的父节点
- `qlNaryTree`：序列化保持层序格式，null 分隔每层

### 3. NEXT_TREE 序列化 `#` 格式修复

**问题**：`qlNextTree` 在每层末尾都加 `#`，但 LeetCode 格式只在「有下一层」时加 `#`，最后一层不加。

**修复**：`qlNextTree` 只在 `!q.isEmpty()`（还有下一层）时才加 `#`。

### 4. 环形链表 `pos` 参数支持

**问题**：LeetCode 的 `hasCycle` 题目需要 `pos` 参数指定环入口位置（如 `head = [3,2,0,-4], pos = 1`），但 `parseListNode` 只能创建线性链表。

**修复**：
- 新增 `parseListNodeWithCycle(s, pos)`：先创建线性链表，再把尾节点的 `next` 指向第 `pos` 个节点
- 新增 `nextPosParam(p, currentIdx)`：从输入段中查找 `pos = X` 参数
- `parseExpr` 的 ListNode case 改为调用 `parseListNodeWithCycle`
- `qlListNode` 加入环检测（`visited` Set），避免环形链表序列化死循环

### 8. JSON 通用序列化优化（CodeRunner 重构）

**背景**：原来每新增一种数据类型要改 3 处（`parseExpr` switch + `printLine` switch + `HELPERS_BASE` 静态方法），`CodeRunner.java` 膨胀到 1666 行、78 个 switch case、79 个静态方法。

**方案**：新增 `HELPERS_JSON` 文本块（`Json` 类），用 JSON 通用解析/序列化替代手写方法：

- `Json.parse(json, type)`：按类型字符串递归解析任意嵌套结构（`int`/`List<Map<String,Integer>>`/`int[][]` 等）
- `Json.serialize(obj)`：Java 对象 → JSON 字符串
- `parseExpr` 从 40 case 减到 4 case（ListNode/TreeNode/Node/default→Json.parse）
- `printLine` 从 40 case 减到 4 case
- `HELPERS_BASE` 从 820 行减到 60 行（只留 split/value/nextPosParam）

**结果**：`CodeRunner.java` 从 1666 行减到 1179 行（-29%），新增标准类型零改动。

### 9. parseSignature 参数名剥离

**问题**：AI 生成的签名带参数名（如 `int[] twoSum(int[] nums, int target)`），`parseSignature` 把 `int[] nums` 当成类型，生成 `(int[] nums) Json.parse(...)` 编译失败。

**修复**：新增 `stripParamName()`，把最后一个空格后的合法标识符视为参数名去掉：`int[][] matrix` → `int[][]`、`int target` → `int`。

### 10. 输入省略号（...）容错

**问题**：AI 生成的测试用例用 `...` 表示长数组（如 `[1,2,3,...,499]`），解析器 `Integer.parseInt("...")` 抛 `NumberFormatException`。

**修复**：`parseListNode`、`Json.parseArr`、`Json.parsePrimitiveList` 三个方法都过滤掉 `...` 和空字符串。同时更新 AI prompt 禁止生成 `...`，要求完整列出数值。

## 三、技术讨论

### 容器判题的数据类型维护成本（已解决）

原每新增一种类型要改 3 处（parseExpr + printLine + HELPERS_BASE）。**已实现 JSON 通用序列化**：

- 标准类型（int/String/List/Map/数组/嵌套）→ `Json.parse`/`Json.serialize` 通用处理，新增零改动
- 自定义结构（ListNode/TreeNode/Node）→ 保留手写 parse/serialize，稳定不变
- 结果：CodeRunner 从 1666 行减到 1179 行，新增标准类型零改动

### 函数模式 vs 完整代码模式

讨论了如果让学生写完整代码（含 main 方法）的利弊：
- 优点：系统不需要 CodeRunner，新增类型零改动
- 缺点：学生要自己处理 I/O，错误定位更难（系统无法区分算法错误 vs I/O 错误）
- 结论：教学场景下函数模式的错误反馈质量更高，学生能更快定位问题
